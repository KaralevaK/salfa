# NYC Yellow Taxi Demand Forecast

Учебный Data Science-проект: веб-сервис почасового прогнозирования спроса
на поездки NYC Yellow Taxi.

## Что внутри

| Файл | Назначение |
|---|---|
| `app.py` | Интерфейс Streamlit: горизонт, кнопка, график, метрики, таблица, выгрузка CSV |
| `forecasting.py` | Ядро: валидация истории, сборка 22 признаков, рекурсивный прогноз |
| `best_model.pkl` | Обученная модель `LGBMRegressor` (LightGBM) |
| `history.csv` | Почасовая история спроса за последние 14 дней |
| `tests/` | Тестовые CSV-сценарии и скрипт проверок `run_checks.py` |
| `requirements.txt` | Зависимости Python |

## Как запустить

```bash
pip install -r requirements.txt
streamlit run app.py
```

Если команда `streamlit` не найдена (например, скрипты Python не добавлены в PATH),
используйте `python -m streamlit run app.py`.

Приложение откроется по адресу `http://localhost:8501`.

## Как устроен прогноз

Модель принимает ровно 22 признака и обучена предсказывать спрос на один
конкретный час. Поэтому горизонт 24, 48 или 168 часов строится
**рекурсивно** — по одному часу за шаг:

1. берётся временной ряд из `history.csv`;
2. для прогнозируемого часа собираются календарные и циклические признаки,
   лаги `lag_1, lag_2, lag_3, lag_24, lag_48, lag_168` и скользящие
   mean/median за 24 и 168 часов;
3. окна заканчиваются на часе `t-1`, то есть учитывают только значения,
   известные до прогнозируемого момента, — data leakage исключён;
4. предсказанное значение дописывается в ряд и используется для расчёта
   следующего часа;
5. отрицательные прогнозы обрезаются до нуля.

### Признаки модели (порядок фиксирован)

```
year, month, day_of_week, hour, day_of_year, is_weekend,
hour_sin, hour_cos, dow_sin, dow_cos, year_sin, year_cos,
lag_1, lag_2, lag_3, lag_24, lag_48, lag_168,
rolling_mean_24, rolling_median_24, rolling_mean_168, rolling_median_168
```

### Входные данные

Перед прогнозом история (демо-файл `history.csv` или пользовательский CSV)
проверяется на наличие колонок `pickup_hour` и `demand`, на пропуски, на
повторы и на строгую часовую непрерывность (шаг ровно 1 час), а также на
минимальную длину в 168 часов — иначе лаг `lag_168` вычислить невозможно.
Дополнительно проверяется, что `demand` содержит конечные неотрицательные
целые значения: строки, корректно преобразующиеся в числа, допустимы, но
после проверок `demand` приводится к числовому типу.

## Пользовательский CSV

В приложении можно выбрать источник данных «Загрузить CSV» и использовать
свою историю вместо демо-файла `history.csv`. Приложение само рассчитает все
22 признака — от пользователя нужны только две колонки:

| Колонка | Тип | Описание |
|---|---|---|
| `pickup_hour` | datetime | Дата и час начала интервала, например `2025-12-31 23:00:00` |
| `demand` | целое число ≥ 0 | Фактический почасовой спрос (количество поездок за час) |

Требования к файлу:

- строго почасовой непрерывный ряд (шаг ровно 1 час, без разрывов);
- минимум 168 последовательных часов истории (нужно для `lag_168`);
- без пропусков и конфликтующих дубликатов времени — полностью одинаковые
  строки удаляются автоматически;
- `demand` — конечные неотрицательные целые значения.

Пример минимального корректного файла:

```csv
pickup_hour,demand
2025-12-01 00:00:00,4637
2025-12-01 01:00:00,2168
2025-12-01 02:00:00,1113
...
```

В приложении есть кнопка «Скачать пример CSV» — она генерирует небольшой
синтетический файл правильной структуры (200 часов), чтобы проверить
загрузку. Для реального прогноза используйте фактические данные.

Файл должен представлять почасовой агрегированный спрос NYC Yellow Taxi со
структурой, сопоставимой с данными, на которых обучалась модель.

### Автоматическая обработка

При загрузке CSV приложение автоматически:

- сортирует строки по `pickup_hour`, если они расположены не по порядку;
- **удаляет полностью одинаковые дубликаты** (совпадают и `pickup_hour`, и
  `demand`) — остаётся одна запись на час, и показывается предупреждение
  с числом удалённых строк.

**Конфликтующие значения одного часа** (одинаковый `pickup_hour` с разным
`demand`) **отклоняются**: приложение не агрегирует их автоматически, а
выводит ошибку с указанием проблемного часа. Приложение также **не** заполняет
пропущенные часы — разрыв ряда вызывает ошибку. После очистки обязательно
проверяется наличие минимум 168 последовательных часов истории.

### Временная зона

История должна быть почасовой в **локальном времени Нью-Йорка**
(America/New_York): метки `pickup_hour` — это локальные календарные часы
города, на них обучалась модель. Приложение работает с часами как с
последовательными метками и не выполняет конвертации часовых поясов.
Переходы на летнее/зимнее время (DST) дают сутки с 23 или 25 часами —
такие сутки при загрузке требуют отдельной обработки на стороне подготовки
данных, чтобы ряд оставался строго почасовым. Логика времени в проекте не
изменялась.

## О качестве модели

Модель — градиентный бустинг **LightGBM** (`LGBMRegressor`). Она использует
календарные признаки, лаги (`lag_1, lag_2, lag_3, lag_24, lag_48, lag_168`)
и скользящие статистики (mean/median за 24 и 168 часов) — всего 22 признака.

Подтверждённые результаты на независимой Test-выборке из исходного notebook
обучения модели:

| Сценарий | MAPE | MAE, поездок/час | RMSE, поездок/час |
|---|---|---|---|
| Прогноз следующего часа (one-step) | 6.81% | ≈ 272 | 406.88 |
| Рекурсивный прогноз на 24 часа | 12.36% | ≈ 514 | 784.67 |

Сценарий «рекурсивный прогноз на 24 часа» наиболее близок к режиму работы
приложения при выборе горизонта 24 часа. При увеличении горизонта ошибки
могут накапливаться. Для горизонтов 48 и 168 часов отдельная оценка на Test
не проводилась, и показатели 24 часа на них не переносятся.

Приведённые метрики — результат на тестовой выборке из исходного исследования,
а **не гарантия** точности будущих прогнозов.

## Ограничения

- Прогноз точечный: доверительные интервалы модель не выдаёт.
- Внешних факторов (погода, районы, события) нет — только календарь,
  лаги и скользящие окна.
- Модель обучена на агрегированном городском спросе, без разбивки по зонам.
